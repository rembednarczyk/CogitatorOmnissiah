# Vinted Scanner (Market Search)

## 1. Overview
Searches **vinted.pl** for physical, second-hand copies of the tracked books. This is a direct HTML scraper — it fetches Vinted's catalog search page over HTTP and parses the response. **It does not use any AI / LLM.** (An earlier design intended a Gemini-based search; it was never implemented, and the `@google/genai` dependency and any `GEMINI_API_KEY` reference have been removed.)

## 2. Search Logic (`VintedSyncService.runVintedCheck` in `services/vintedSyncService.ts`)
- **Candidates**: Books from Notion that are NOT already read/owned (excludes the `Przeczytane`, `Biblioteka`, `Biblioteka 9`, `Posiadam` source tags), with a non-empty Polish title.
- **Search URL**: `https://www.vinted.pl/catalog?catalog[]=2319&language_book_ids[]=6440&page=1&order=price_low_to_high&price_from=2&currency=PLN&search_text={title author}` (books category, cheapest first).
- **Request shaping**: Rotates a realistic browser `User-Agent` and sends browser-like headers (`Referer`, `Sec-Fetch-*`, etc.) to reduce bot blocking.
- **Result parsing**: the scanner inspects the HTML for status markers and delegates item extraction to the pure `parseVintedItems(html, title, author)` in `services/vintedParser.ts` (unit-tested on captured HTML/JSON).
  - Bot/anti-scrape markers (`cloudflare`, `captcha`, "robot") → reported as `blocked`.
  - "Brak wyników" / "Nie znaleźliśmy żadnych przedmiotów" → `no_results`.
  - Otherwise `parseVintedItems` extracts up to 5 relevant listing items via four cascading paths: the `data-component-name="Catalog"` JSON blob (legacy — not emitted by the current Next.js page), an `"items":[…]` regex with bracket matching, `feed-grid__item` grid tiles, then a global `href=/items/…` regex. The current live DOM lands on the grid-tile path: Vinted hashes its CSS-module class names (e.g. `Grid-module-scss-module__…__feed-grid__item`), so tiles are matched on the stable `feed-grid__item"` suffix rather than a fixed class, and each tile yields URL (query stripped), title, structural price, currency and thumbnail.
  - **Per item**: `title`, `price` (raw string), `priceValue` (numeric, for sorting — `null` when only a placeholder like "Sprawdź"/"??" is available), `currency`, `url`, and `photo` (an `images1.vinted.net` thumbnail URL; present on the JSON and grid-tile paths, absent on the bare `href` fallback). `parseVintedPrice` normalizes `"25,00"` / `"12.90"` / numbers → a number, placeholders → `null`. When no structural price is found, the item price is recovered from the offer's `title` text (Vinted embeds `…, {price} zł, {price with buyer protection} zł`; the lower of the pair is the item price).

## 2b. Grouping by Seller
Finding "low-hanging fruit" — books available from the **same seller**, so one order can bundle several. Grouping runs **from the store**, not live: resolve sellers into the blob (§2c stage 2), then load the stored data (§2c stage 3), and the pure `groupBySeller` turns it into bundles. (The earlier live on-demand grouping — a `/api/vinted-group` endpoint with "Najtańsze"/"Wszystkie oferty" buttons that fetched sellers without persisting — was removed once the persistence pipeline superseded it; it re-fetched every time and threw the results away.)
- **Seller extraction**: `extractVintedSeller(html)` reads two stable, unique markers from the offer page — the profile link `href="/member/{id}"` (id) and `data-testid="profile-username"` (login) — returning `{ id, login, url }` (login `detach`-ed, since the offer page is ~2 MB).
- **`groupBySeller`** keeps each seller's **cheapest copy per book**, returns sellers holding **≥2 distinct books**, and computes the **premium vs the book's global-cheapest** offer so the UI shows the shipping-vs-item tradeoff per book and per bundle (`premium` / `totalPremium`). It's a pure function fed by `storedToView` — grouping/rendering is entirely client-side.
- **Bundle ordering** is a pure `sortBundles(bundles, mode)` with a UI toggle: `count` (default — most books first, ties broken by cheapest total) or `price` (cheapest `totalValue` first, ties broken by most books). It returns a copy without mutating the input; `groupBySeller` delegates to `sortBundles(.., "count")` for its default.

## 2c. Persistence (Notion blob) — decouples acquisition from analysis
Scraping is rate-limited and unreliable (Cloudflare); analysis (grouping) is cheap and repeatable. Persisting scan results into Notion separates the two: scrape once, analyse many times, and make the scan **resumable** across runs (the ~160-books-per-run limit stops losing progress).
- **Store**: a compact JSON blob in a `VintedData` rich_text property on each book row (`services/vintedStore.ts`: `StoredVintedData = { scannedAt, offers[] }`). The adapter chunks it into ≤2000-char rich_text segments (`saveVintedData`); the mapper rejoins them (`getPlainText` → `NotionBook.vintedData`).
- **Write path** (stage 1): the scan persists per book best-effort (`persistBookOffers`) after each response — matches, or an empty-offers record that still stamps `scannedAt` (scan coverage). `createColumnIfNeeded("VintedData")` ensures the property once per run; a failure disables persistence without failing the scan.
- **Merge + change detection**: `mergeAndDiff` keeps a previously-resolved **seller** and `firstSeenAt` for any offer whose URL survives (so a re-scan doesn't wipe seller data), drops vanished offers, and enters new ones stamped with `firstSeenAt = scannedAt`. It also records `prevPrice` (last scan's price) and returns a diff (`added` / `removed` / `priceDropped` / `priceRaised`); the book's `changedAt` is bumped to `scannedAt` only when something actually changed. The stored view surfaces this as per-book "zmiana" and per-offer "nowa" / "−X zł" (price drop) badges, and the scan's debug line shows a `Δ` summary. A re-scan that comes back blocked or empty **never** overwrites the stored blob (see §3), so change detection isn't fooled by a failed fetch.
- **Seller resolution** (stage 2): `resolveSellersToStore` walks stored offers whose `seller` is `null`, fetches each offer page, and writes the seller back into the blob (one Notion write per book). It's **incremental and resumable** — resolved sellers persist, so a run only tackles remaining `null`s and re-running continues where it stopped. By default there's **no cap** (a run resolves all remaining nulls, as many as it manages before it finishes or the connection drops — the per-book write means a dropped run still keeps its progress); the rate is bounded by the throttle, not a total count. An optional `cap` in the request body limits a single run. Task `vinted-resolve-sellers` / `POST /api/vinted-resolve-sellers`; UI button "Ustal sprzedawców (baza)".
- **From-store view** (stage 3): `GET /api/vinted-stored` reads every book's blob and returns the offers+sellers; the pure `storedToView` maps that to the same `VintedResult[]` + `url→seller` map the live scan uses, so tiles and seller bundles render **from the store, no re-scrape** (`useVintedStored`, "Wczytaj z bazy" button). Each tile shows its `scannedAt`, and a banner shows the freshness range — the loop closes: scan + resolve sellers in chunks over days, then analyse instantly and repeatedly from the store. The store view also carries Notion metadata straight from the book row (not scraped): the publication **year** (`Rok`), the **cycle** membership (`Część cyklu`), and — when the harvest ritual has resolved them — the **cycle name** (`Cykl`) and **volume number** (`CyklNr`), all propagated through `StoredBookView`/`VintedResult` and the live-scan `match` result alike. The UI renders these as an **interactive cycle tile** (`src/components/CycleTile.tsx`): a `partOfCycle` book shows a clickable `Layers` chip labelled `Cykl · N` when the volume number is known (else plain "cykl"); clicking opens the shared `CyclePanel` (`useCycle` → `GET /api/cycle`) with the ordered volume list and read-order — the exact same preview used in Skryptorium. The panel is a **click-anchored popover** rendered via a portal to `document.body` (so `position: fixed` escapes framer-motion transforms on the ancestor cards) and positioned by the pure `computePopoverPosition` helper: it anchors beside the clicked chip, flips above/below toward the larger free space, and caps its height to the viewport so long cycles scroll internally instead of being clipped or landing off-screen. The same tile rides through to the **seller bundles** (`SellerBundleEntry.bookCykl` / `bookCyklNr` / `bookPartOfCycle`), so a consolidated order shows which of its books are cycle volumes, which volume, and lets you check the reading order in place.

## 3. Reliability & Anti-Bot Pacing
- **Session priming** (`services/vintedSession.ts`, knob `vinted.primeSession`, default on): once per run — before the first catalog request, and again before the seller-resolution pass — the service does a single GET of the Vinted homepage and harvests its `Set-Cookie` (Cloudflare's `cf_clearance` plus Vinted's anonymous-session cookies) into a `Cookie` header carried on every subsequent request. Crucially the priming request's **User-Agent is pinned for the whole run** and reused on the catalog/offer requests — `cf_clearance` is bound to the UA, so the usual per-request UA rotation would invalidate the clearance. It's best-effort: a failed prime or a homepage that sets no cookies yields an empty session and the scan proceeds unprimed with per-request UA rotation (previous behaviour). Priming is skipped when there are no candidates. **Self-heal:** a primed session (pinned UA + cookie) can make Vinted serve a different page variant whose catalog isn't inlined — which would silently drop every offer (200 OK, 0 parsed). So after priming the service fires one validation probe (the first candidate's catalog URL) and, if the page is neither blocked nor structurally a catalog (no `data-component-name="Catalog"`, no feed-grid, no `/items/` links, no no-results marker), it discards the session and scans unprimed. Net effect: priming can help against blocks but can never reduce hit rate. The seller-resolution pass (stage 2) primes the same way and runs its own self-heal on the first offer page (drops the session when `extractVintedSeller` can't parse it), so priming can't silently break seller identification either.
- **Browser priming** (`services/browserPrime.ts`, knob `vinted.primeWithBrowser`, default off): the heavier anti-block variant. A plain homepage GET can't clear a full Cloudflare **JS challenge** — this drives a headless Chromium (`playwright-core`, an optional dependency, dynamically imported) to the homepage so the challenge script actually runs, then harvests the resulting cookies (a real `cf_clearance`) plus the browser's own User-Agent into the same `VintedSession`, which the lightweight axios path then reuses. It's fully best-effort: no `playwright-core`, no Chromium binary, a launch/navigation error, or no `cf_clearance` within the timeout all yield `null` and the flow falls back to the plain HTTP prime (and then to an unprimed scan). It needs a Chromium available to the backend process — works when the app runs somewhere with a browser (a local machine, a host that has one); a browserless host (e.g. a minimal Render dyno) simply falls back. The binary is located via `VINTED_CHROMIUM_PATH`, else `PLAYWRIGHT_BROWSERS_PATH`, else playwright-core's own resolution; a standard `HTTPS_PROXY` is honored. **Caveat:** `cf_clearance` is partly bound to the client's TLS/JA3 fingerprint, so a browser-minted cookie can still be rejected by a plain axios request — but the catalog self-heal detects that and drops the session, so browser priming can help against blocks and never lowers the hit rate. If it proves insufficient, the next step is the full variant (scrape catalog pages through the browser itself). Pure cookie join (`parseSetCookie`) is unit-tested; disable via the config panel if it ever misbehaves.
- **Timeout**: 45 000 ms per request (via a keep-alive `https.Agent`).
- **Throttling**: 3–5 s delay (with jitter) between books — applied on **every** path, including the no-results case, to avoid the request bursts that trigger Cloudflare blocks.
- **429 handling**: On HTTP 429 waits ~5 s before continuing; 403 is surfaced as a Cloudflare block.
- **Cancellation**: Cooperative — checks the cancellation token each iteration and reports `cancelled: true` on the `complete` event when stopped.
- **Source tagging**: a book that has offers on Vinted (a match) gets a `Vinted` tag added to its `Źródło` multi-select in Notion (`addTagToMultiSelect`, best-effort, skipped when the book already carries the tag). It only adds the tag; it isn't removed if the offers later disappear. `Vinted` is not in the scan's exclusion list, so tagged books keep being re-scanned.
- **Resumable / oldest-first scan**: candidates are always scanned **oldest-`scannedAt` first** (never-scanned first), so an interrupted run (the ~160-books-per-container limit, or a mobile drop) always advances the stalest data, and a resumed run naturally continues on the not-yet-done books. The "Kontynuuj" checkbox (default on) additionally skips books scanned within the last **`skipScannedWithinHours`** (12 h — i.e. the current batch), so it finishes leftover/older books instead of re-doing today's. It's **hours, not days**, on purpose: with a multi-day window, "yesterday's" leftovers (still < window) were all skipped and the run did nothing. Uncheck it to re-scan everything (still oldest-first), refreshing offers while keeping resolved sellers via `mergeAndDiff`. A book only gets a `scannedAt` when it's actually scanned (a match, or a genuine empty on first sight): **blocked** and **errored** books are deliberately left un-stamped so a resume retries them — which means a run drowning in Cloudflare blocks makes little forward progress by design. The `complete` event carries `blocked`/`errors` counts and appends them to the summary ("Nie zeskanowano N …"), so a resume that seems stuck is visibly the block, not the resume logic.

## 4. Frontend Integration
- **Hook**: `useVintedCheck` opens the SSE stream and renders progress, per-book search attempts, and matched listings.
- **Trigger**: The "Skaner Artefaktów Vinted" section (Vinted tab).
- **Output**: A `search_attempt` event per book (status + item count) plus `match` events with the found listings.
- **Offer display** (`VintedCheckItem`): per book the offers are sorted cheapest → dearest via `sortOffersByPrice` (price-less offers sink to the end); the card header shows `od {min} zł · {count}` (`offersPriceSummary`), the cheapest offer is badged "najtańsza", and each row renders the offer thumbnail (falling back to a placeholder icon), the formatted price (`formatVintedPrice`, Polish style), and the offer title. Helpers live in `src/utils/vintedOffers.ts` (pure, unit-tested).

## 5. Notes
- Vinted's markup and anti-bot behaviour change over time; treat the HTML parsing as best-effort and expect occasional `blocked` results from a datacenter IP.
